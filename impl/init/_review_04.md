The displayed table has only `ID / KIND / STATUS / SLUG`. The data isn't available from `/stacks/{name}` either: `daemon.writeItemSummaryListJson` only emits id/slug/kind/status. Either extend the item summary JSON to include the routing target, or have the CLI fan out to `/stacks/{name}/items/{id}` per item. Cheap workaround: include target in the summary on the daemon side. The two acceptance criteria in `04_cli_read.md` are still met (all read commands work; rendering is from API response data), but this is a gap against step 4's literal wording.
- `src/cli_stack.zig:96-134` — `runShow` deviates from plan step 4 ("GET `/stacks/{name}` plus `/stacks/{name}/items`") by only issuing the composite GET and reusing the inlined items array. Functionally equivalent because the daemon inlines items, but the comment block at line 104-108 then 129-131 contradicts itself ("we do two GETs rather than one because the daemon's `/stacks/{name}` endpoint already returns both" — but only one GET is done). Either issue the second GET as planned, or simplify the comment to match the implementation.
- `src/cli_stack.zig:296-310` — the brace walker uses `var depth: usize = 0; depth -= 1` on `}`. The initial `{` increments depth to 1 so well-formed daemon output is safe, but any stray `}` would underflow `usize` and panic. Items list values can technically include arbitrary text via slug/id; even though `isValidStackName` / `isValidId` constrain inputs upstream, this is fragile and asymmetric with the rest of the CLI's defensive parsing. Switch to `isize` or guard `if (depth > 0)`.
- `src/cli_stack.zig:188-204` — `findJsonStringField` walks `\\` as an escape but does not unescape the returned slice; the daemon's `writeJsonString` emits `\\"`/`\\\\`/`\n` escapes, so values containing escaped characters print with the backslashes intact (e.g. a description with `"` would render as `He said \"hi\"`). The daemon's normal output mostly avoids these, but item/stack names with double quotes or backslashes would render wrong. Worth a TODO since the plan calls for rendering "without extra formatting" and currently the CLI applies *less* formatting than needed.
- `src/cli_stack.zig:237-263` — `renderStackConfig` ignores OOM on `extractJsonStringArray` (catches with `... catch null`). If allocation fails inside the helper... it can't, the helper doesn't allocate. So the `catch null` only swallows `error.NotFound`, which is fine. Cleaner to write `extractJsonStringArray(...) catch |e| switch (e) { error.NotFound => null, else => return e }`, since the current form would silently eat a future allocating variant of this helper.
- `src/cli.zig:369` — `runInit` keeps `yes = parsed.yes or true` from milestone 2/3, which short-circuits the `-y` flag (always true). Pre-existing carryover, not introduced here, but worth flagging when this milestone touches `cli.zig`.
- `src/http_client.zig:100-105` — `loadTokenIfPresent` swallows every error including OOM with `else |_| {}`. Plan step 7 says "the plumbing should not be reworked in milestone 5"; an OOM disguising as "no token" is the kind of bug milestone 5 will trip over once mutations require the token. Surface the OOM, treat only `error.FileNotFound` (and possibly `error.AccessDenied`) as "no token".
- `src/http_client.zig:30` — `pub const ClientError = anyerror;` widens the public surface to all errors, identical pattern to milestone 3's `TokenError = anyerror` and `StartError = ... || anyerror`. Same critique applies: callers can't exhaustively switch and the named sentinels (`DaemonNotRunning`, `BadResponse`, `BadFlagValue`) are not enforceable. Worth tightening before milestone 5 starts threading mutation errors through this client.
- `src/cli.zig:236-239` — `dispatch` returns exit code 2 for unknown subcommands and prints usage; the dispatch test expects "unknown subcommand" substring in stderr. Works, but the format `stako: unknown subcommand \`{s}\`` uses backticks which differ from POSIX convention (`'foo'` or `"foo"`). Cosmetic.
- `src/cli.zig:401-410` — `printDaemonUsage` does not document `--foreground` even though `parseDaemonArgs` accepts it. Same file: the top-level `printUsage` says `daemon, d  start|stop|st` but elides `status` (canonical) — only the short alias is shown. Inconsistent with `printStackUsage` which shows both forms.
- `src/cli.zig:206-207` — `parseStackArgs` rejects any positional that starts with `-` via `if (std.mem.startsWith(u8, a, "-"))` *before* the positional bucket. Side-effect: a stack name beginning with `-` cannot be passed (unusual, but `--` separator support would be the standard escape hatch). Acceptable for v1 since `isValidStackName` likely rejects leading `-` anyway.
- `test/cli_tests.zig:395-402` — the libc `setenv` hack to honor `STAKO_PORT` works but ties the test to `link_libc = true` for the entire test binary (build.zig line 196). `std.process` does not expose `setenv` portably; the comment in build.zig calls this out. Optional alternative: use a `--port` flag in the test invocation, plus a separate small in-process unit test that hand-builds the `Opts` struct to exercise the env precedence. Reduces blast radius of libc-linking in one test.
- `test/cli_tests.zig:463-474` — the subprocess test silently skips (`return error.SkipZigTest`) if `zig-out/bin/stako` doesn't exist. `build.zig` wires `run_cli_tests.step.dependOn(b.getInstallStep())`, so the binary should always be present. Recommend turning the skip into an explicit failure since the dependency is now declared.
- `src/cli_stack.zig:208-235` — `renderStackList` walks every `"name":` key in the body. Works for the current daemon shape, but if a future endpoint adds a non-stack `"name":` field (e.g. an identity name in the response envelope), this scanner will treat it as a stack name. Plan disallows CLI-local stack parsing but a structured JSON parse on the response body wouldn't violate that — it'd just be safer. Optional pre-milestone-5 cleanup.

## Acceptance criteria

- **All read commands work against a running daemon** — MET. `cli: stack list`, `cli: stack show`, `cli: stack config` each spin up an ephemeral daemon and assert canonical + short-alias output. Subprocess test exercises argv → main → dispatch path.
- **`--json` / `-j` produces machine-readable output without extra formatting** — MET. `cli: stack list --json passes the daemon body through unchanged` asserts the daemon's JSON envelope appears verbatim (`"stacks":[` substring) and the human header `NAME\n` is absent. Implementation writes `resp.body` + `\n` and returns.
- **Clear error message when daemon isn't running ("daemon not started; try `stako daemon start`")** — MET. `cli: connection refused prints the daemon-not-started hint` asserts both `daemon not started` and `stako daemon start` substrings on stderr. Mapping: `tcpConnectToAddress` → `error.ConnectionRefused` → `error.DaemonNotRunning` → canonical message in `reportClientError`.
- **No CLI-local stack-parsing logic — all rendering uses API response data** — MET. `cli_stack.zig` only parses JSON bodies returned by the daemon (cheap grep + brace walker), never touches `stacks/<name>/stack.toml` or item meta files. Storage reader lives in the daemon process; CLI doesn't import `storage.zig` or `stack_config.zig`. (See non-blocking note about replacing the cheap grep with a structured JSON parse.)
- **Every common command and flag has a documented short equivalent** — MET. Canonical → short: `stack`→`s`, `daemon`→`d`, `list`→`ls`, `show`→`sh`, `config`→`cfg`, `status`→`st`, `--json`→`-j`, `--root`→`-r`, `--port`→`-p`, `--verbose`→`-v`. All documented in `printUsage` / `printDaemonUsage` / `printStackUsage`, all asserted by `StackAction.fromString` / `DaemonAction.fromString` / `Subcommand.fromString` unit tests, all exercised by integration tests via paired runs.
