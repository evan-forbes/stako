# Audit — Milestone 4: CLI Read Path

Baseline: 1caaf4f. Modules audited: `src/cli_stack.zig` (734 lines), `src/http_client.zig` (328 lines). Tests audited: `test/cli_tests.zig` (22 tests covering both M4 and M8/M2/M5 paths; the M4-owned subset is ~12 tests) plus in-file `test` blocks in `cli_stack.zig` (5) and `http_client.zig` (6).

Baseline confirmed: `zig build test --summary all` → 389/389 pass on the second run. A first run failed with one unrelated abort in `runtime_tests.test.daemon SSE endpoint: when wired, streams a published event` (signal 6 inside `mainServer`); it is consistently flaky outside M4 scope (the runtime_tests file belongs to M6), and retrying produces all-green. This is *not* M4-owned; flagging only so the reader knows why an earlier `--summary all` may print "1 failed".

## Execution traces

**Trace A — `stako stack list` happy path.** `main.zig` skips argv[0]; `cli.dispatch` matches `Subcommand.fromString("stack") = .stack`; `runStack` → `parseStackArgs` builds `StackArgs{.action=.list, .flags=ApiFlags{.root="."}}`; `cli_stack.run` calls `http_client.open(allocator, .{.root="."})`. `open` calls `config_mod.loadFromRoot` (overlays `config.toml` then `config.local.toml`), takes `cfg.daemon.port`; `STAKO_PORT` is not set so we skip the env branch; `opts.port_override` is null. `loadTokenIfPresent` opens `.stako/local_token` — if present, reads `stat.size` bytes, trims trailing `\r\n`, dupes the trimmed slice, frees the original. Client returned with `port=7421, token=<owned>, host="127.0.0.1"`. Back in `runList`, `http_client.get(client, "/stacks")` calls `request(self, "GET", "/stacks", null)`: `parseIp("127.0.0.1", 7421)`, `tcpConnectToAddress`, writes a request with `Host`, `Connection: close`, `Accept: application/json`, `Authorization: Bearer <token>` headers and no body. Read loop accumulates response into `resp_buf`, capped at 8 MiB and bailing on any `stream.read` error (see Important #1). `parseResponse` finds `\r\n\r\n`, parses the status line, scans headers for `content-length`/`transfer-encoding`, slices/duplicates the body. `runList` checks `resp.status == 200`, then in non-JSON mode calls `renderStackList` which substring-scans for `"name":"` keys, writes a `NAME` header and one row per stack. Resource lifecycle: stream closed in `request`'s `defer`; req_buf, resp_buf, raw all freed; `resp.deinit` frees the body slice in `runList`'s `defer`.

**Trace B — daemon returns 404.** Same path through `cli.dispatch` to `runShow("nope")`. `runShow` builds `/stacks/nope` via `allocPrint`, defers free. The HTTP request roundtrips and `parseResponse` returns a `Response{.status = 404, .body = "{\"error\":{\"code\":\"not_found\",\"message\":\"stack not found\",\"details\":{\"stack\":\"nope\"}}}"}`. `runShow` sees `status != 200`, calls `reportApiError` which substring-greps the body for `"code":"` (→ `not_found`) and `"message":"` (→ `stack not found`) using `findJsonStringField`. Prints `stako: HTTP 404 not_found: stack not found\n` to stderr. Returns exit 1. Verified by `cli: stack show unknown stack -> non-zero exit + canonical error`.

**Trace C — daemon not running (transport-level).** `runList` calls `http_client.get`; inside `request`, `std.net.tcpConnectToAddress(addr)` raises `error.ConnectionRefused` (Linux refuses to a closed port — the `--port=1` trick in the test). The switch on line 159 maps to `error.DaemonNotRunning`. `runList`'s catch arm calls `reportClientError(error.DaemonNotRunning, …)`, which writes `stako: daemon not started; try \`stako daemon start\`\n`. When `--verbose` is set, a second line appends `  attempted: http://127.0.0.1:1/stacks`. Returns exit 1. The canonical-message contract is asserted by `cli: connection refused …` and the verbose append by `cli: --verbose …`. Note: the http_client maps `error.ConnectionRefused` to `error.DaemonNotRunning` but `reportClientError` switches on *both* names — defensive but harmless.

**Trace D — `--port` overrides every other source.** `parseStackArgs` populates `flags.port_override = 4242`. `http_client.open` runs the full resolution chain (config → env → override): `opts.port_override` is applied last (line 98) so it wins. No CLI test exercises the precedence stack end-to-end (config + env + flag simultaneously); see Coverage gaps.

## Use-after-return / UAR scan

Explicitly scanned every function in `cli_stack.zig` and `http_client.zig` for the previously-fixed pattern (a `[N]T` stack array sliced and returned, or a `*[N]T` taken to local storage and surfaced past the frame). Findings:

- **`cli_stack.zig:267` `arr_buf: [16][]const u8`** — the previously-fixed site. `extractJsonStringArray(body, …, &arr_buf)` now takes caller-owned storage; the returned `[]const []const u8` aliases `arr_buf` (caller-owned) and its element slices alias `body` (caller-owned by `renderStackConfig`). Used inline within the same function, never escapes. **Safe.**
- **`cli_stack.zig:676` `buf: [16][]const u8`** — same shape, inside a unit test. Same safety. **Safe.**
- **`http_client.zig:189` `tmp: [4096]u8`** — scratch read buffer. Used as `tmp[0..n]` and immediately `appendSlice`'d (deep-copy) into `resp_buf`. The slice never escapes the loop. **Safe.**
- **No other stack arrays** detected via `grep 'var.*: \[[0-9]'` across M4 sources.

Beyond the literal stack-array-sliced pattern, scanned for return-an-alias-of-stack-local patterns generally: `findJsonStringField`/`findJsonRawField`/`extractJsonStringArray` all return slices of their `body` argument (caller-owned). `parseResponse` returns `body_owned` from `allocator.dupe`/`decodeChunked` (heap-owned). `loadTokenIfPresent` returns a fresh allocation. `readPromptFile` returns a fresh allocation. **No UAR found.**

## Important

- **Important** — `src/http_client.zig:190-196` — **Read-loop silently swallows transport errors.** `const n = stream.read(&tmp) catch break;` treats *every* read error as graceful EOF — including `ConnectionResetByPeer`, `WouldBlock`, `BrokenPipe`, `OperationAborted`, etc. A mid-response RST therefore presents to `parseResponse` as a truncated response that may still pass framing (if it lands on a chunk boundary in `decodeChunked`, the last chunk is silently dropped; if `Content-Length` is present the existing `body_raw.len < len` guard catches it; if neither header is set, *the truncation is invisible*). The daemon emits a Content-Length for every JSON response, so in practice this is masked — but the moment SSE or chunked endpoints come into play (M9 HTML, the existing `/stacks/{name}/events`), a truncated read produces a partial body the CLI happily renders. Fix: at minimum, distinguish "got 0 bytes" (clean EOF) from "got an error before EOF" and surface the latter as `error.TransportError`. The audit prompt explicitly listed "transport timeout" as an audit dimension; this is the same class of bug.

- **Important** — `src/http_client.zig:159-201` — **No socket-level read/write/connect timeout.** `tcpConnectToAddress` uses the OS default connect timeout (Linux: ~127 s for the SYN backoff). `stream.read` blocks indefinitely with no `SO_RCVTIMEO`. A daemon that's accepted the connection but is stuck (deadlock, gdb-stop, kernel page-fault stall) leaves the CLI hanging forever with no way for the user to abort other than ctrl-C. The plan's audit-dimensions list includes "transport timeout" specifically. Add `setsockopt(SO_RCVTIMEO)` (e.g. 10 s, configurable via `--timeout` or hard-coded for v1) and likewise on connect via `connect`-with-timeout. No test exercises this path.

- **Important** — `src/http_client.zig:81-85` — **Any config-load error silently falls back to default port.** `var cfg = config_mod.loadFromRoot(...) catch break :blk;` swallows *every* error from `loadFromRoot`, not just `FileNotFound`. The comment on line 79-80 ("Config files are optional; missing `.stako/` is tolerated") matches the intent, but a real bug — a malformed `.stako/config.toml`, a `PortOutOfRange`, an I/O error — silently downgrades to port 7421. The user then sees `daemon not started` even though their actual daemon is on port 8080. Narrow the catch to `error.FileNotFound, error.RootNotADirectory` and forward the rest. (M3 audit `_audit_03.md` flagged the same class of bug for the daemon side; the CLI side has it too.)

- **Important** — `src/cli_stack.zig:142-145` and `src/cli_stack.zig:118-121` — **Stale/misleading comment in `runShow`.** The block comment on line 117-121 says the CLI does two GETs (`/stacks/{name}` + `/stacks/{name}/items`), and the comment on line 142-144 doubles down on "pull items separately". The actual implementation does *one* GET on `/stacks/{name}` and parses the inlined `"items":[…]` array out of the composite payload. The plan's step 4 originally asked for two GETs, but the daemon now inlines items in the composite response and the CLI takes advantage of that. The comments are dead and actively misleading the next reader. Either delete the comments or update them to match.

- **Important** — `src/cli_stack.zig:226-247` (`renderStackList`) — **Stack-list scanner over-matches.** The loop greps for `"name":"…"` substrings across the *entire* response body, with no awareness of JSON structure. The current daemon shape — `{"stacks":[{"name":"a"},{"name":"b"}]}` — is fine because no other field is named `"name"`. The moment the daemon adds a top-level metadata `"name":"stako"` (e.g. for a future API-version stamp) or an inlined provider with a `"name"` field, the CLI prints those too. The render path is one of the M4 acceptance items ("render as a human-readable table") so brittleness here matters. The same brittleness applies to `findJsonStringField` in `renderStackConfig` — `"description":"…"` could legitimately appear in a nested object's child. A narrow JSON walker that descends into `"stacks":[` first (analogous to the items walker in `renderStackShow`) would be one step less brittle without pulling in `std.json`.

- **Important** — `test/cli_tests.zig` — **No `--json` `-j` test for `stack show` or `stack config`.** Only `cli: stack list --json` exists. The plan's acceptance criterion *"`--json` / `-j` produces machine-readable output without extra formatting"* is asserted for one of three read commands. The plumbing is shared, but the show path has the extra wrinkle of containing nested structures (config + items) so a `-j` snapshot would catch any future "let's pretty-print before passthrough" regression.

- **Important** — `test/cli_tests.zig` — **No tests for 401/403 (bad token), 500/502 (5xx body shape), or stale daemon (pid file exists but process is dead).** Only the 404 case is covered. The audit prompt explicitly named all of "transport timeout", "bad token", "pagination/large response" as paths to trace. A `runCli` test that points at a daemon serving a fake 401 response (e.g. via a `serveOne` that returns a hand-rolled body) would assert `reportApiError`'s code-extraction path works for non-404 codes. 5xx coverage is especially missing because `reportApiError` makes no distinction between 4xx and 5xx — both return exit 1.

## Minor

- **Minor** — `src/cli_stack.zig:266` — **Missing space in formatted output**: `"  default_workdir:{s}\n"` (no space after the colon). Compare to the sibling lines which all read `"  description:    {s}\n"`, `"  created_at:     {s}\n"`, etc. Cosmetic, but the column doesn't line up.

- **Minor** — `src/cli_stack.zig:338-340` — **Renderer reads from `kind`/`status`/`slug` but the column layout assumes these are short.** Header is `{s:<6} {s:<10} {s:<10} {s}` (ID 6, KIND 10, STATUS 10, SLUG rest). An item kind of `"compact_chained"` (15 chars) blows past the 10-wide pad. Not a correctness bug — Zig's `{s:<10}` just emits the full string with no truncation — but the table becomes mis-aligned silently. Either widen the column or truncate with ellipsis.

- **Minor** — `src/cli_stack.zig:201-217` — **`findJsonStringField` quietly accepts unterminated strings.** If the body ends mid-string with no closing `"`, the function returns `null` rather than `body[start..body.len]`, which is correct — but the same loop also silently accepts `\X` for any X including `\u` (the JSON `\uXXXX` form), advancing only one byte past the backslash. Hex chars (`0-9a-fA-F`) don't include `"` so it works by accident. Add a one-line comment noting the limitation, or extend to skip 5 bytes after `\u`.

- **Minor** — `src/cli_stack.zig:648-656` (`readPromptFile`) — **Missing `errdefer` for the allocated buffer.** `buf = try allocator.alloc(...)` then `_ = try f.readAll(buf)` — if `readAll` errors, `buf` leaks. The only fallible call after the alloc is `readAll`, but adding `errdefer allocator.free(buf)` makes it future-proof and matches the pattern in `loadTokenIfPresent`.

- **Minor** — `src/cli_stack.zig:653-654` (`readPromptFile`) — **Race between `stat.size` and `readAll`.** Alloc is sized off the stat; if the file shrinks between calls (concurrent editor save, file truncated), the unread tail of `buf` remains uninitialized and is then included verbatim in the POST body. Defensive fix: capture the readAll return value and shrink to it (or use `readToEndAlloc` with the 1 MiB cap).

- **Minor** — `src/cli_stack.zig:564-593` (`postAndReport`) — **Unused `allocator` parameter** (line 573 `_ = allocator;`). Drop it from the signature for clarity; every call site already has a local allocator.

- **Minor** — `src/cli_stack.zig:539-562` (`runConfigSet`) — **Sends every `--set` value as a JSON string.** `paused=true` becomes `{"paused":"true"}` — a string, not a boolean. The M5 daemon may or may not coerce; either way this is an M5 concern, not M4. (Including only because this file mixes M4 and M5 logic and the same scan covers both.)

- **Minor** — `src/http_client.zig:30` — `pub const ClientError = anyerror;` — `anyerror` is the universal error set and the alias buys nothing over just writing `!Response` directly. The docstring acknowledges this. Either inline the `anyerror` or define a narrower set (the actual sites only return five named errors: `DaemonNotRunning`, `BadResponse`, `BadFlagValue`, plus `OutOfMemory`/IO from the I/O calls). Minor stylistic noise.

- **Minor** — `src/http_client.zig:157-158` — `std.net.Address.parseIp` failure is mapped to `error.BadResponse`. That's misleading; the *response* hasn't even started. A name like `error.BadHost` or letting the underlying `error.InvalidIpAddress` propagate would be clearer. In practice `host` is always `"127.0.0.1"` so this branch is dead; still worth labeling correctly.

- **Minor** — `src/http_client.zig:280-321` — **`parseResponse` tests don't cover the `body_raw.len < len` truncation guard.** A one-line `expectError(BadResponse, parseResponse(a, "HTTP/1.1 200 OK\r\nContent-Length: 100\r\n\r\nshort"))` would close that gap.

- **Minor** — `test/cli_tests.zig:127-133` — `startEphemeralDaemon` is a one-liner trivial wrapper; consider inlining or moving to the daemon-tests helper module so M4 and M3 share one definition.

## Coverage gaps

1. **Port-resolution precedence.** No test exercises `--port > STAKO_PORT > config.local.toml > config.toml > default` end-to-end. The STAKO_PORT test (`cli: STAKO_PORT env override is honored`) covers env-vs-default; nothing covers env-vs-flag or env-vs-config.
2. **Bad-token / 401 path.** Acceptance criterion implies authentication wiring; only 404 is tested for non-200 daemon responses.
3. **5xx path.** No test that the CLI reports `HTTP 500` with a reasonable code/message extraction.
4. **Transport timeout / hang.** No test that the CLI eventually gives up against an unresponsive (accepted-but-silent) socket. Plan/audit prompt explicitly call this out.
5. **`--json` for `show` and `config`.** Only `stack list -j` is tested.
6. **`stack show` without items.** No test that the empty-items branch prints `(no items)`.
7. **`stack list` with zero stacks.** No test that the empty-stacks branch prints `(no stacks)`.
8. **Large response.** No test that responses near or beyond the 8 MiB cap are handled (truncate behavior is currently silent — see Important #1).
9. **Chunked transfer encoding from the daemon to the CLI.** `parseResponse` has a chunked-decoder unit test, but no end-to-end test forces the daemon to chunk; the daemon today always uses Content-Length, so the chunked path is unexercised by integration.
10. **`--root` pointing at a non-existing or non-initialized directory.** `cli.open` swallows config errors and tries to use 7421; we never assert the right user-visible behavior in that case.
11. **`Authorization: Bearer …` header actually goes on the wire when the local_token is present.** No test inspects the request the CLI sends.
12. **Stale-process tolerance.** `daemon status` test covers "stopped" but not "stale pid file pointing at a dead process".

## Strengths

- **The previously-fixed UAR is genuinely fixed.** `extractJsonStringArray` now takes caller-owned `out: [][]const u8` storage and the call site at `cli_stack.zig:267-268` correctly holds the `arr_buf` in `renderStackConfig`'s frame for the lifetime of the rendered output. The test on line 674 is the right shape too. The fix did not leave any sibling occurrences elsewhere in M4.
- **`reportClientError` honors the documented contract.** The acceptance criterion *"A clear error message when the daemon isn't running (\"daemon not started; try `stako daemon start`\")"* is implemented verbatim and asserted both with and without `--verbose`. The verbose-mode `attempted: http://…:…/path` suffix is a nice touch that helps real-world triage.
- **Memory hygiene is consistently disciplined.** `Response.deinit` always frees the body; `runShow`/`runConfig`/`runList` all use `defer resp.deinit()`. The `allocPrint`'d paths have matching `defer allocator.free(path)`. `Client.deinit` frees the optional token. `buildItemBody` uses `errdefer` on the ArrayList and `toOwnedSlice` returns ownership cleanly. The `errdefer` on `resp_buf` (`http_client.zig:188`) is technically unreachable after `toOwnedSlice` but it's defensive and free.
- **The JSON-passthrough rule (`--json`) is followed everywhere.** Each `--json` arm writes `resp.body` verbatim to stdout, never modifies it, and emits exactly one trailing `\n`. The M4 acceptance criterion that `-j` produces machine-readable output without extra formatting is upheld.
- **No CLI-local stack parsing.** Per the acceptance criterion, every rendered field comes from the daemon's JSON response. `renderStackConfig` and `renderStackShow` only consume `body: []const u8`; nothing in the CLI reads `stack.toml` directly.
- **Argument parser cleanly separates global and per-action flags.** `ApiFlags` factors out the four shared knobs (`--json`, `--root`, `--port`, `--verbose`); each action layers on its own (`--target`, `--prompt-file`, `--slug`, `--set`). The unit-test suite in `cli.zig` (16 parser tests, end of file) covers every short alias.
- **Header construction is correct.** `Connection: close` matches the read-until-EOF loop; `Accept: application/json` and `Content-Type: application/json` are both set; `Authorization: Bearer` is conditional on a token being loaded. Content-Length is only emitted when a body is present.
- **Subprocess test exists.** `cli (subprocess): stako stack list against a live daemon` exec's the compiled binary, exercising the real argv → `main()` → `dispatch` path that the in-process tests cannot reach.
- **Trimming of trailing CR/LF in `local_token` is correct and bounded.** The `loadTokenIfPresent` shrink-and-dupe pattern is unusual but each step is well-justified, and the zero-after-trim case correctly returns null.
