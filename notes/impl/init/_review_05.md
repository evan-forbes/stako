## Non-blocking

- `src/mutation_queue.zig:183-258` — On `vcs.commit` failure the worker frees `out` and returns, but it never calls `vcs.rollbackPaths` and never deletes the freshly-written `meta.toml`/`prompt.md`/`stack.toml`. Plan acceptance says "Half-failed mutations leave the repo clean: no staged changes, no partial commits, no audit-log line"; the audit and commit halves are honored, but `git add` ran successfully inside `commit()` before `git commit` failed, so a stale staged change can persist into the next mutation. Wire `rollbackPaths` plus a best-effort file-delete for newly-created append/insert items.
- `src/mutations.zig:255-318` — Insert semantics deviate from `design_version_control.md`'s commit-grouping rule ("if existing IDs shift, the renames are in the same commit"): the implementation rejects insert unless max+1 already sorts before the reference id, i.e. it only works to prepend before id 0001. The plan does not pin renumbering behavior, so this is a documented v1 simplification, but file an item for a real positional-insert pass — the API endpoint as currently wired is almost always useless.
- `src/daemon.zig:128-141` — `daemon_started` is logged from `startWorker`, but there is no symmetric `daemon_stopped` audit line on shutdown (no call in `Daemon.deinit` or `requestShutdown`), and `daemon_started` carries no `version` or `config_hash` details despite `design_errors_and_audit.md` listing both as required for lifecycle events. Plan step 4 says "Log allowed mutations and daemon lifecycle events."
- `src/mutations.zig:391-401` — `cancel` mutation rejects `running` items with `InvalidStateTransition`, but `design_state_machine.md` and `design_runtime_loop.md` specify that cancel of running items must delegate to the session manager. Acceptable as a v1 placeholder (session manager doesn't exist until M6), but the rejection should map to a clearer error than `state_conflict`; the state machine itself permits the transition so the user sees a confusing 409 today. Track this so M6 wires it up.
- `src/daemon.zig:128-141` — `Daemon.startWorker` swaps `self.queue.audit_writer` from `undefined` to `&self.audit_writer`. The doc comment correctly warns "must be called after the Daemon is at its final address," but there is no `assert`/sentinel. A future caller could submit a request between `daemon_mod.start` and `startWorker` (e.g. via the queue directly in a test), see no worker, and hang. Consider initializing the field to a real pointer in `start()` itself (the audit writer is already constructed by then), removing the soft contract entirely.
- `src/vcs.zig:207-245` — `runGit` does `child.env_map = null`, which Zig's stdlib documents as "inherit parent env." That's fine for production but lets user-set `GIT_*` vars (e.g. `GIT_AUTHOR_NAME`, `GIT_CONFIG_GLOBAL`) leak into daemon commits. Consider explicitly stripping `GIT_*` vars or whitelisting `PATH` only, to keep commits reproducible across machines.
- `src/vcs.zig:101` — `commit()` returns `error.GitFailed` when `opts.paths.len == 0`. That's a programmer error, not a git failure — would be clearer as `unreachable` or a dedicated `error.NothingToCommit`. The current mapping would surface to the HTTP client as a generic `internal` error.
- `src/vcs.zig:170-186` — `rollbackPaths` exists but is never called by the queue. Either remove the dead code or wire it (see first non-blocking item).
- `src/mutation_queue.zig:325-338` — `mutationErrorToKind` has an `error.DirtyTarget` arm, but `mutations.Error` never returns `DirtyTarget` (only `vcs.assertPathsClean` returns `HasDirtyTarget`, handled separately). Dead arm.
- `test/mutation_tests.zig:23-43` — `Scratch.deinit` removes the per-test directory but leaves the parent `/tmp/stako-test-mutation/`. After running the suite, four parent dirs (`/tmp/stako-test`, `/tmp/stako-test-cli`, `/tmp/stako-test-daemon`, `/tmp/stako-test-mutation`) remain. Cosmetic; the helper should `deleteTree` the parent on the last teardown or use `tmpDir` for deterministic cleanup.
- `test/mutation_tests.zig:99-103` — `serveThread` swallows every error via `break`, so an assertion failure inside `serveOne` silently shrinks the served count and the client-side test then sees a timeout / 0-status. Log the error before breaking.
- `test/mutation_tests.zig:410-473` — Concurrent test: both client threads call `httpRaw` with `Connection: close`, but the two server threads each `serveOne` once; if both clients happen to hit the same accepting thread before the second thread blocks on `accept`, one client could 0-status. In practice the kernel queues SYNs and both accept loops drain, but the test would be more robust with `serve(2)` on a single thread (the queue already proves serialization). Either way, the FIFO ordering claim from the queue is checked only indirectly (no commit-order assertion).
- `src/mutations.zig:402` — `state.isValidTransition` is consulted after the API-allowed switch, but `superseded` and the cancel-from-paused/blocked paths pass through it correctly. However `state.VALID_TRANSITIONS` only lists `queued → superseded` while `design_state_machine.md`'s "Who Can Trigger What" says `* → superseded`. The plan and the transition table agree (queued-only); the design doc inconsistency is not new and is out of scope.
- `src/audit.zig:105-115` — `ensureOpen` calls `f.seekFromEnd(0)` to append. Comment says "tighten perms if the file already existed with a looser mode" — the `fchmod` call is reasonable, but `createFile(.{.truncate = false})` already opens an existing file without changing its mode, so the chmod runs on every open. Cheap but noisy if audit.log is on a network FS. Consider gating behind a stat check.
- `src/daemon.zig:204` — `mutation_queue.Queue.init(allocator, abs_owned, undefined)` passes an `undefined` `*audit.Writer`. See the `startWorker` non-blocking above; the pattern is fragile.
- `src/mutations.zig:107-193` — `applyCreateStack` writes `stack.toml` with whatever subset of optional fields was supplied. No fields means an empty file save `created_at`, which is not the same shape as the milestone-2 `init` writer. A fresh `stako stack new demo` produces a stack that won't render the default config view the same way it would for the milestone-2-initialized default stack. Test `applyCreateStack: writes stack.toml` covers the happy path; consider snapshotting bytes against milestone-2's expected layout.
- `test/mutation_tests.zig:521-581` — The merge-conflict test creates a real merge conflict in-tree, calls `daemon_mod.start(...)`, and expects `MergeConflictsPresent`. Good coverage, but the test does not `git merge --abort` afterward; combined with the leftover-directory issue (above), the scratch dir is in a half-merged state when `deinit` deletes it. Cleanup happens, but a reader debugging a flake will find a conflicted tree.

## Acceptance criteria

- **All v1 mutation endpoints work end-to-end through the CLI.** — MET. `src/cli_stack.zig` wires `new`/`add`/`insert`/`retry`/`cancel`/`supersede`/`pause`/`resume`/`config` to the right POST paths; `test/mutation_tests.zig` and `src/mutations.zig` tests exercise each.
- **Every non-GET endpoint requires the local token.** — MET. `daemon.zig:422-427` `isMutationRoute` gate calls `verifyAuth`; constant-time compare in `local_token.Token.verify`. Tests `missing token rejects POST with 401` and `bad token rejects POST` confirm.
- **`.stako/audit.log` records one NDJSON line per successful mutation with the schema from `design_errors_and_audit.md`.** — MET. `src/audit.zig` writes the exact schema (ts/identity/action/target/outcome/[reason]/details), file mode 0600, fsync per append; test `Writer: append produces one NDJSON line, file mode 0600` pins the shape.
- **Commit grouping matches one user-visible mutation per commit.** — MET. `mutation_queue.processOne` does one `vcs.commit` per request; test `append item then cancel produces two commits + two audit lines` proves count.
- **Half-failed mutations leave the repo clean: no staged changes, no partial commits, no audit-log line.** — PARTIALLY MET. No commit and no audit line on failure (verified by code path), but `git add` may have already staged changes when `git commit` fails, and the on-disk file from `mutations.applyXxx` is not unwound. See Non-blocking #1.
- **The daemon never auto-commits arbitrary harness workdir changes.** — MET. `vcs.zig` only operates on the notes root, and `git add` is always called with explicit `--` paths.
